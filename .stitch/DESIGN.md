# Fit Manager — Local Frontend Design System

## Overview

Fit Manager uses a stark, warm, high-contrast visual system for a gym-management SaaS. The interface alternates large ink-black regions with near-white paper surfaces, then uses saturated orange as the primary interaction and emphasis color. Sand and warm amber support the orange without becoming independent themes.

The operational product is moderately dense: dashboard metrics, lists, tables, forms, member status, payments, entries, and platform administration are grouped into compact bordered surfaces. Marketing and authentication screens are more spacious. Hierarchy comes from heavy type, uppercase tracked labels, strong light/dark section changes, and orange accents before it comes from shadow.

The implemented personality is direct, sturdy, and energetic rather than decorative. Corners stay between 4px and 8px, most controls are at least 44px high, and cards use thin borders. There is no glass treatment, no icon-led decoration, and no ornamental blur.

The application declares `color-scheme: light`. There is no dark-mode toggle or `dark:` variant system. Ink sections are intentional dark surfaces inside one fixed light scheme, not a second mode.

Source precedence for this extraction is the current rendered `/` and `/login` interface, then the current local TSX/CSS working tree. Protected product screens were source-reviewed but could not be browser-rendered without an authenticated local session.

### Role mapping

- **Page background:** `paper`.
- **Elevated surfaces and cards:** `paper`; dark feature cards use `charcoal` on `ink` sections.
- **Navigation/sidebar:** `ink`, with `charcoal` hover/secondary surfaces.
- **Primary action:** `primary` with `ink` text; hover uses `primary-hover` with `paper` text.
- **Secondary action:** either `ink` with `paper` text on light surfaces, or transparent with a `gray`/`charcoal` border on dark surfaces.
- **Accent:** `accent-sand` for tracked labels on ink; `accent-amber` appears only inside the authentication gradient.
- **Text:** `ink` on light surfaces and `paper` on dark surfaces.
- **Muted text:** `gray` on light surfaces and `gray-light` on dark surfaces.
- **Borders:** `gray` or `charcoal` for strong separation; `gray-light`, `border-light`, and `surface-subtle` for light separation.
- **Inputs:** transparent or `paper` fill, `gray-light` border, `ink` text.
- **Success:** the emerald surface/border/text set above.
- **Warning:** `warning-surface`, `accent-sand` border, and `charcoal` or `ink` text. Member warnings use `accent-sand / 30%` with a `primary` border.
- **Error:** the red surface/border/text set above. Member danger uses `primary-hover` as its border/text exception.
- **Informational:** no independent blue palette is visible. `blue-50`, `blue-100`, and blue legacy utilities resolve to paper/gray/ink aliases.
- **Disabled:** current foreground/background plus `opacity: 0.6`; no separate disabled color token.
- **Selection:** `primary` background with `ink` text.
- **Global focus:** 3px solid `primary`, offset 3px.

### Transparency and gradient

- Authentication gradient: `linear-gradient(135deg, #000000 0%, #C10801 34%, #F16001 68%, #D9C3AB 100%)` via `--brand-gradient`.
- Modal scrim: `rgb(0 0 0 / 80%)` through `bg-black/80`.
- Sidebar context panel: `rgb(51 51 51 / 50%)` through `bg-charcoal/50`.
- Warm member warning: `rgb(217 195 171 / 30%)` through `bg-brand-sand/30`.
- Light borders use `gray-light` at 50% or 60% where coded.
- No backdrop blur is implemented.

### Compatibility aliases and resolved conflicts

The current global CSS deliberately remaps older arbitrary Tailwind values. Use the rendered role, not the literal class spelling:

| Legacy utility value | Current rendered value and role |
| --- | --- |
| `#083F88` or `#061F46` backgrounds/text | `ink` (`#000000`) |
| `#FF7A1A` background/text/accent | `primary` (`#E85002`) |
| `#F6F9FC` background | `paper` (`#F9F9F9`) |
| Hover `#E86305`, `#062E64`, or `#062F66` | `primary-hover` (`#C10801`) with `paper` text |
| Focus border `#083F88` | `primary` (`#E85002`) |
| `bg-[#FF7A1A].text-white` | Orange background with `ink` text, overriding the class name’s apparent white text |

`text-gray-dark` appears repeatedly in components but no `gray-dark` theme token or generated utility exists. It therefore inherits the nearest text color, normally `ink`. This is an implementation exception, not a new color.

## Typography

### Font source and family

No web font, local font file, `@font-face`, or `next/font` configuration is active. `font-sans` resolves in the rendered interface to:

```css
-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue",
"Noto Sans", Arial, sans-serif, "Apple Color Emoji", "Segoe UI Emoji",
"Segoe UI Symbol", "Noto Color Emoji"
```

All UI, marketing, metrics, forms, and labels use this one system sans stack. There is no implemented serif or monospace design role.

### Usage rules present in the interface

- Marketing headings use weight 700; operational headings, values, actions, and labels frequently use weight 900 (`font-black`).
- `font-semibold` is 600, `font-bold` is 700, and `font-black` is 900. Weight 500 is not used as a visual role.
- Body copy is normally 16px/24px. Explanatory marketing copy uses 18px/32px.
- Uppercase labels establish section and metric hierarchy. Implemented letter spacing values are `0.08em`, `0.12em`, `0.14em`, `0.16em`, `0.18em`, and the facial-enrollment exception `0.20em`.
- Numeric dashboard text uses the same system sans and heavy weights; there is no tabular-number or monospace feature setting.
- Headings use normal tracking unless an uppercase eyebrow is attached. No negative heading tracking is implemented.

## Layout

### Spacing rhythm

The frontend uses Tailwind’s 4px base rhythm, but not a reduced custom scale. Actual recurring values are:

| Token/class family | Value | Main use |
| --- | --- | --- |
| `1` | 4px | tight metadata offset, small gaps |
| `2` | 8px | compact gaps, input label offset, small padding |
| `3` | 12px | list gaps, control vertical padding |
| `4` | 16px | card/list padding, grid gaps |
| `5` | 20px | default page/card padding and horizontal CTA padding |
| `6` | 24px | form sections, panel gaps, module-header padding |
| `8` | 32px | desktop content padding, section gaps, CTA offsets |
| `10` | 40px | authentication vertical/horizontal padding and brand spacing |
| `12` | 48px | large desktop gutters and auth illustration padding |
| `16` | 64px | marketing section vertical padding |
| `24` | 96px | desktop hero vertical padding |

Common rules:

- App and platform content: 20px padding by default, 32px from 640px.
- Marketing horizontal gutters: 20px base, 32px from 640px, 48px from 1024px.
- Cards and panels: usually 20px; marketing dark cards and module headers use 24px; the module header becomes 32px from 640px.
- Form groups: 24px between sections, 16px inside sections, 8px from label to control.
- Control groups and list rows: 12px–16px gaps.
- Marketing sections: 64px vertical; hero increases to 96px from 1024px.

### Maximum widths

The implementation uses Tailwind max-width utilities rather than one global content container:

- `max-w-sm`: 384px.
- `max-w-md`: 448px for auth cards/forms.
- `max-w-lg`: 512px.
- `max-w-xl`: 576px for hero/supporting copy.
- `max-w-2xl`: 672px for module descriptions and centered section headings.
- `max-w-3xl`: 768px for hero text and the facial-access dialog.
- `max-w-5xl`: 1024px for member forms and dev surfaces.
- `max-w-6xl`: 1152px for loading/detail wrappers.
- `max-w-7xl`: 1280px for landing navigation and hero content.

### Application and platform shells

- Root shell is a full-height grid only from 1024px: `292px minmax(0, 1fr)`.
- The 292px ink sidebar has 20px padding, a right `charcoal` border, gym/platform context panel, navigation, user identity, and sign-out button.
- Below 1024px the sidebar becomes a full-width top region with a bottom border. It is not an off-canvas drawer and has no collapse control.
- App navigation is a two-column grid by default, four columns from 640px, and one column in the 1024px sidebar.
- Platform navigation is two columns by default, three columns from 640px, and one column from 1024px.
- Active navigation is an orange rounded rectangle with ink text. Inactive links use light-gray text and charcoal/paper hover feedback.
- The content region uses `min-width: 0` to prevent grid-content overflow and changes from ink shell to paper surface.

### Header behavior

`ModuleHeader` is a full-width ink panel with:

- 8px radius.
- 1px charcoal border plus 4px orange top border.
- 24px padding, increasing to 32px at 640px.
- Sand uppercase eyebrow.

## Elevation & Depth

Depth is mostly tonal and bordered:

- Paper cards sit on paper or ink backgrounds and are separated by 1px borders.
- Ink headers and sidebars establish the strongest hierarchy through contrast rather than elevation.
- `shadow-sm` appears on operational cards: `0 1px 3px 0 rgb(0 0 0 / 10%), 0 1px 2px -1px rgb(0 0 0 / 10%)`.
- `shadow-2xl` appears on the landing dashboard preview and facial-access dialog: `0 25px 50px -12px rgb(0 0 0 / 25%)`.
- The landing preview applies `shadow-black/40`, raising that shadow color to 40% black.
- The facial modal uses an 80% black scrim and no backdrop blur.
- No inset shadows, glassmorphism, frosted surfaces, or layered blur are implemented.

## Shapes

- Default small rounding: 4px via `rounded`.
- Interactive controls and compact cards: 6px via `rounded-md`.
- Main cards, panels, images, and dialogs: 8px via `rounded-lg`.
- Pills and initial avatars: full radius.

## Do's and Don'ts

- Do preserve the current semantic roles: orange for primary interaction, ink/paper for dominant surfaces, sand for warm secondary emphasis, emerald for success, and red for error/danger.
- Do use the current system sans stack and the implemented 600/700/900 hierarchy.
- Do preserve the 4px spacing rhythm, 6px controls, 8px cards, 44px common control height, and current responsive grid behavior.
- Do keep status meaning in text as well as color.
- Do preserve table overflow wrappers and current minimum widths instead of squeezing table columns.
- Do keep product terminology already present, including `Miembros`, `Membresias`, `Pagos`, `Entradas`, `Ingresos`, `Gimnasio activo`, and the implemented status labels.
- Do treat legacy blue/orange arbitrary utilities according to their current global compatibility remapping.
- Don't introduce dark-mode variants; the current system is one fixed light color scheme with intentional ink sections.
- Don't introduce new colors, fonts, icons, gradients, shadows, radii, motion, placeholder copy, or absent component types when reproducing this system.
- Don't treat `text-gray-dark` as a confirmed token; it currently inherits because no utility is generated.
- Don't use old literal class names such as `#083F88` as visible color evidence when global CSS remaps them.
- Don't make pills the default shape; they are reserved for badges and circular initials.
- Don't add hover movement; implemented hover behavior is chromatic only.

## Accessibility Patterns

Confirmed implementation only:

- Global `:focus-visible` is a 3px solid orange outline with a 3px offset.
- Auth controls also have explicit focus border/ring utilities.
- Form controls have visible labels; member search uses an `sr-only` label tied by `htmlFor`/`id`.
- Common interactive targets are at least 44px high; the facial verification action is 48px.
- Active navigation exposes `aria-current="page"`.
- Auth success/error uses `status`/`alert` roles.
- Loading skeleton exposes `role="status"` and an `sr-only` label.
- Facial dialog exposes `role="dialog"`, `aria-modal="true"`, and `aria-labelledby`; it traps keyboard focus, closes on Escape, and restores trigger focus.
- Camera/product asides carry accessible labels where implemented.
- Images in current TSX include descriptive alt text; captured facial image uses `Foto facial capturada`.
- Reduced-motion behavior is globally implemented.
- Status panels include textual labels and explanations rather than relying only on color.
- No broad claim of WCAG conformance is made. Landing navigation has no mobile replacement below 768px, and protected screens were not browser-audited in an authenticated session during this extraction.

## Known Inconsistencies and Exceptions

- The dominant current system is the custom black/orange/sand theme. Numerous components still spell old arbitrary blue/orange values in class names; global CSS overrides their visible result.
- Operational surfaces mix two border vocabularies: newer custom `charcoal`/`gray` borders and older aliased `slate-200`/`slate-300` borders. Preserve the exact component context; do not average them into one invisible border.
- Cards are usually paper, but `bg-white` also resolves to paper, so there is no actual white-versus-paper elevation difference.
- Button weight is not fully normalized: auth uses 600, marketing commonly 700, and operational actions commonly 900.
- Error color has two active systems: Tailwind red for form/load errors and brand red for member danger/primary hover.
- `text-gray-dark` is unresolved and inherits; no new gray-dark value should be invented.
- Shadows are secondary and inconsistent by surface: auth cards have none, operational cards use `shadow-sm`, landing preview/modal use `shadow-2xl`.
- The landing page hides desktop navigation links below 768px without adding a mobile navigation control.
- There is no runtime theme switcher or tenant-specific theme profile in the current implementation.
